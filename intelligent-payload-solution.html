Core Engine
The Corrected Topology Classifier
No NAS. Uses geo-clustering + concurrent incident count + cross-partner correlation.
FOR EACH INCIDENT:

Step 1: Geo-enrich
  → Map each device to lat/lng (87% coverage)
  → Find nearest splitter via HAVERSINE (where partner has splitters)
  → Compute: geo_spread = max distance between devices

Step 2: Classify by geo-spread + concurrency

  ┌────────────────────────────────────────────────────────────────────────────┐
  │                                                                            │
  │  geo_spread < 500m                                                       │
  │  AND concurrent_partner_incidents < 5                                      │
  │  → SPLITTER / LOCAL FIBER FAULT                                           │
  │    Pin: centroid lat/lng of affected devices                               │
  │    Action: "Technician bhejein is location pe" + Maps link                 │
  │                                                                            │
  │  geo_spread > 3km  OR  concurrent_partner_incidents >= 10                  │
  │  → PARTNER OLT / POP / POWER FAILURE                                     │
  │    Signal: whole network down, not localized                               │
  │    Action: "Check OLT/power at your POP" or "DG set chalao"               │
  │                                                                            │
  │  Multiple partners in same geo-area going down within 15-min window       │
  │  → ISP BACKBONE / BACKHAUL FAULT                                          │
  │    Signal: cross-partner correlation                                       │
  │    Action: "ISP issue. Hum escalate kar chuke hain. Aap kuch mat karo."   │
  │                                                                            │
  │  Single device, no neighbors down                                        │
  │  → CUSTOMER DEVICE / POWER ISSUE                                          │
  │    Action: Auto-send restart SMS to customer                               │
  │                                                                            │
  │  500m-3km spread, 5-10 concurrent                                          │
  │  → TRUNK FIBER / PARTIAL OLT                                              │
  │    Action: "Multiple splitters affected, check main fiber trunk from POP"  │
  │                                                                            │
  └────────────────────────────────────────────────────────────────────────────┘

Step 3: Enrich with context
  → Recurrence: same geo-cluster had outage N times in 14 days?
  → Customer pain: tickets/calls from these devices?
  → Time: night? → morning queue with priority
  → Partner history: what's this partner's P50 for this type?

Step 4: Generate payload
  → Claude API: structured JSON → Hindi/Hinglish WhatsApp message
  → Include: Google Maps deep link, action, negative actions

What Complaint Overlay Adds to Intelligent Payload

  • Second detection layer: When 3+ customers in the same geo-cluster raise "supply down" tickets within 2 hours — flag as probable outage even if V2.1 didn't detect it
  • Severity amplifier: An outage WITH customer complaints is more urgent than one without. Bump priority when complaint overlay matches.
  • False positive filter: If V2.1 detects an outage but zero customers complain AND no tickets match — may be a detection artifact. Lower priority.
  • Complaint-driven pins on map: Orange pins for "customers complaining here but no outage detected" — partner should investigate this location too.
What We Need From You
Ground Knowledge Required to Make This Perfect
These are questions only someone with operational/ground knowledge can answer. Data alone won't tell us.
Network Topology

How does the physical network actually work?

  • OLT ownership: You said OLTs are partner-level. Does each partner have exactly 1 OLT at their POP? Or can large partners have multiple OLTs? Is OLT info stored anywhere in Snowflake (we couldn't find it)?
  • Splitter topology: Is there a strict hierarchy (OLT → trunk fiber → splitter → customer)? Or can splitters be daisy-chained (splitter → splitter → customer)?
  • Device-to-splitter mapping: Is there a direct FK anywhere (device → splitter_id)? Or is HAVERSINE proximity our only option? 436 partners have 0 splitters mapped — is that a data gap or do those partners use a different infra model?
  • ISP backhaul: How does ISP fiber reach the partner's OLT? Is it a dedicated fiber or shared POP? Can we identify which ISP serves which partner?
Cross-Partner Correlation

How do we detect ISP-level vs partner-level faults?

  • ISP-partner mapping: Which ISP(s) serve which partner? Is this in any table? Knowing this lets us correlate: "3 partners on ISP-X all went down → ISP issue"
  • Geographic POP sharing: Do multiple partners share an ISP POP in the same area? If so, is there a mapping of partner → POP location?
  • The mega-partner (ID 274877906948): This single partner has 100-195 undetected supply-down tickets/day spread across 10° lat/lng (entire North India?). Is this a master/aggregator account? Should we exclude it?
Detection Blind Spots

Why are 52% of supply-down complaints undetected?

  • Ping monitoring threshold: V2.1 needs 3 consecutive failed pings + 15 min. Could intermittent/partial outages (customer has 50% packet loss but not 100%) slip through? Does the customer perceive "down" even at partial loss?
  • Authentication-based outages: If ISP authentication fails but ping is technically alive (device responds to ICMP but can't pass traffic) — would V2.1 miss this?
  • Customer device vs WG device: Customer complains about WiFi being down. Is the WG router still pinging but the customer's WiFi router (behind it) is the issue? How common is this?
  • Speed/quality issues classified as "supply down": Customer has 2 Mbps instead of 50 Mbps. They say "internet down." But device is pinging. How many of the 6,509 undetected tickets are actually quality issues?
Geo Signal Interpretation

How should we read geographic patterns?

  • Typical splitter coverage radius: How far (in meters) does a typical splitter serve? Is 500m a reasonable clustering threshold?
  • Fiber trunk paths: When we see devices go down in a line (not a circle), that suggests a trunk fiber cut. Is there any data on fiber routing paths?
  • Power grid correlation: In areas with frequent power cuts, many devices go down simultaneously but it's not a fiber/OLT issue. Is there any power grid data (DG set status, area power outage feeds) we could integrate?
  • Urban vs rural patterns: Does the same geo-spread mean different things in dense urban (Delhi) vs semi-rural areas? What's the typical splitter density in each?
Frontend & Partner Behavior

How do partners actually work?

  • Partner's daily workflow: When a partner gets a WhatsApp alert, what do they physically do? Do they dispatch a technician? Do they go themselves? Do they have a control room?
  • Technician communication: How does the partner tell their field tech where to go today? Phone call? WhatsApp group? Our map link needs to fit this existing flow.
  • Language/literacy: Hindi/Hinglish for most? Any regional language needs? How technical can the messages be? Do partners understand "OLT" and "splitter" or do they call them something else?
  • Multi-ISP partners: Partners serving both Wiom and other ISPs — do they have separate OLTs per ISP? Or shared infrastructure? This affects diagnosis.
  • What phone/browser do partners use? Android version? WhatsApp default browser? This affects the map view. Leaflet works on most, but low-end phones may struggle with heavy maps.
