Core Insight
The Network Topology IS the Root Cause Engine
You don't need ML to diagnose most outages. The topology pattern tells you.
ISP Backbone (city-wide fiber ring)
  │
  ├── POP / OLT-A ─── serves Partner 1, Partner 2, Partner 3
  │     ├── Splitter S1 (28.576°N, 77.220°E) ── [D1] [D2] [D3]
  │     ├── Splitter S2 (28.577°N, 77.221°E) ── [D4] [D5]
  │     └── Splitter S3 (28.578°N, 77.219°E) ── [D6] [D7] [D8]
  │
  └── POP / OLT-B ─── serves Partner 4, Partner 5
        ├── Splitter S4 ── [D9] [D10]
        └── Splitter S5 ── [D11] [D12]

FAULT AT SPLITTER S1?
  → D1, D2, D3 are down. D4-D8 are fine.
  → Diagnosis: Fiber/splitter fault at S1 location.
  → Action: Send technician to 28.576°N, 77.220°E

FAULT AT OLT-A?
  → D1-D8 all down (all splitters under OLT-A). OLT-B is fine.
  → Diagnosis: OLT/ISP link failure.
  → Action: Call ISP NOC. Don't touch anything.

FAULT AT ISP BACKBONE?
  → D1-D12 all down (both OLTs). Multiple partners affected.
  → Diagnosis: ISP backbone/POP failure.
  → Action: ISP auto-escalation. Tell all partners: "ISP is handling it."
The diagnosis algorithm is just set arithmetic on the topology tree. Which level of the tree has ALL children down? That's where the fault is. No ML needed for the primary classifier — deterministic logic on topology + timing.
Solution Architecture
Five Layers of Intelligent Payload
Each layer adds intelligence. Layer 1 alone solves 60% of the problem. Each subsequent layer refines.
Layer 1 — Geo-Cluster Diagnosis (Deterministic)

"Where exactly is the problem?"

For every incident, map each impacted device to its nearest splitter using HAVERSINE on lat/lng. Then check:

  • All devices cluster around 1 splitter → Splitter/fiber fault at that location. Partner knows EXACTLY where to go.
  • Devices span multiple splitters but share 1 NAS/OLT → OLT-level or ISP uplink fault. Partner can't fix this. Call ISP.
  • Devices span multiple NAS IDs / multiple partners → ISP backbone fault. Auto-escalate to ISP.
  • Single isolated device, no neighbors down → Device-level fault. Customer power or device issue.

Output: Fault location pinpointed to a lat/lng with Google Maps deep link. Fault level classified: SPLITTER / OLT / ISP / DEVICE.

Buildability: Pure SQL + Python. Splitter proximity already confirmed working (avg distance 44m). 12 hrs: doable.

Layer 2 — Temporal Pattern Classification

"What kind of failure is this?"

The timing of how devices went down tells you the failure mode:

PatternSignatureRoot Cause
Cliff-dropAll devices in cluster go 100% → 0% within same 5-min windowFiber cut or power failure — sudden, total
CascadingDevices go down in sequence over 15-30 min, spreading outward from a pointSplitter/joint degradation — partial, spreading
Simultaneous multi-clusterMultiple splitter clusters under same OLT go down within minutesOLT or ISP uplink failure
IntermittentDevices flap: down → up → down. Ping bitmap shows gaps (e.g. "110100110010")Loose connector or power fluctuation
Single device, others fineOne device down, all geo-neighbors operationalCustomer-side issue (power, device reboot)

Buildability: Analyze CREATED_AT timestamps of devices within an incident + ping bitmap from hourly health table. Pattern matching, not ML.

Layer 3 — Contextual Intelligence (AI-Powered)

"What has happened here before? What makes this incident special?"

This is where Claude API / LLM adds real value — not for the core diagnosis, but for contextual enrichment:

  • Historical pattern — "This splitter has had 4 outages in the last 14 days. Previous ones were fiber-related and took avg 6 hours to resolve. Consider proactive replacement."
  • Customer pain signal — "2 customers on this splitter have already called CS. Priority: HIGH."
  • Partner context — "This partner's historical P50 for similar incidents is 388 min. Fast partners resolve this type in 45 min."
  • Time-of-day awareness — "It's 11 PM. Your night resolution rate is 3x worse. Here's exactly what to do now vs what can wait for morning."
  • Natural language synthesis — Combine all signals into a clear Hindi/Hinglish WhatsApp message.

Buildability: Claude API call with structured incident context as input → natural language output. 4-6 hrs.

Layer 5 — Delivery Interface

"Deliver the payload WHERE the partner already is."

  • Primary: WhatsApp message with diagnosis + action + map link (partners already read these — 77.6% read rate)
  • Secondary: Live map view — a single-page web app per partner showing all active incidents as pins, colored by severity, clickable for diagnosis and action
  • Conversational: Reply-based status — partner replies "status" to get current state; replies "done" to mark resolved; replies "help" to get detailed troubleshooting steps

Why This Works
Three Design Principles That Make This Scalable

1. Topology-first, not ML-first

Most "AI root cause" solutions try to train a model on historical data. We don't need that for the primary classifier. The network topology IS the diagnosis. Same splitter = fiber. Same OLT = ISP. Multi-OLT = backbone. This is deterministic, explainable, and works from day one with zero training data.

AI (Claude API) is used where it actually adds value: contextual synthesis and natural language generation, not for the core classification.

2. Location is the payload, not a dashboard

Most outage systems show maps in dashboards that partners never open. We flip it: the Google Maps link IS the alert. Partner taps one link, sees exactly where to go. No dashboard login, no portal, no app download. The map opens in WhatsApp.

3. Negative actions are as important as positive ones

"Do NOT restart devices" during an OLT failure. "You can't fix this — ISP is handling it." These negative instructions are as valuable as positive ones. Today's generic alert causes wrong actions. The intelligent payload prevents waste by telling partners what NOT to do.

The Innovation
Partner's Live Outage Map
Replace 20 text alerts with one live map. Each pin = one fault location. Tap for diagnosis + action.

What the Partner Sees

A single-page web app (works in WhatsApp in-app browser) showing:

  • Red pins — Active faults YOU need to fix (splitter/fiber issues at specific locations)
  • Amber pins — ISP-side issues (you can't fix these, we're escalating)
  • Grey pins — Self-resolving / customer-side (no action needed)
  • Tap any pin → diagnosis card: root cause, action, affected customer count, time since down
  • Green route line — suggested dispatch route if multiple red pins (nearest-first)

This replaces: "You have 20 incidents today" with "You have 3 locations to visit. Here's the route. 2 other issues are ISP-side, we're handling them."

Why a Map Beats a Dashboard

  • Zero learning curve — every partner already uses Google Maps daily
  • One-tap navigation — tap the pin, tap "Directions", Google Maps takes over
  • Bandwidth protection — 20 alerts become 3 pins. Cognitive load drops 85%
  • No app download — works as a web link in WhatsApp. Opens in-app browser.
  • Technician-friendly — partner forwards the map link to their technician. Technician follows the route.
